# System Architecture Overview: Arc

> Application code exists for spec 001 (Groups & Knowledge Sections), spec 002 (Arc HUD design system), spec 003 (Sessions with a brain and workers), spec 004 (Change review), spec 005 (Commands and skills in sessions), spec 006 (Stepping in on a worker) and spec 007 (Codex as a second provider). Choices evidenced by that code are stated plainly; items marked _(assumption)_ describe parts not built yet and still need confirmation.

---

## 1. Application & Technology Stack

- **Desktop shell:** Electron with TypeScript, scaffolded with electron-vite. Electron is the most mature option for running and supervising many child CLI processes from a Node main process, and it can host real terminals (node-pty) if the planned plain-shell and "Open in macOS Terminal" specs need them. _Rejected: Tauri (process supervision and any later PTY work would be more work)._
- **Pinned versions (from `package.json` and `pnpm-lock.yaml`):** Electron 44.8.0, TypeScript 6, Svelte 5, Tailwind CSS 4, zod 4, Drizzle ORM 0.45 with better-sqlite3 13, chokidar 4.0.3 (exact), `@modelcontextprotocol/sdk` 1.31.0 (exact), electron-log 5, Vitest 5, Playwright 1.64, pnpm 10.29.3, Node >=22 (`engines`).
- **UI framework:** Svelte 5 (runes) + Vite in the renderer, styled with Tailwind CSS v4 through `@tailwindcss/vite`. _Rejected: React._
- **HUD design system (renderer):** every screen is built from one shared look so later screens (sessions, workers) reuse it.
  - **Design tokens:** `src/renderer/src/styles/tokens.css` defines the Tailwind `@theme` (the default palette is reset, so only Arc colors exist): near-black navy ground with a faint grid, cyan primary, amber for needs-attention/warnings, green for done, red for errors, plus size, shadow, focus-ring and duration tokens. Fonts are bundled locally via `@fontsource` (Orbitron and Rajdhani for display and labels, JetBrains Mono for data, paths and code); OFL licenses ship in `resources/licenses/`.
  - **Component library:** `src/renderer/src/lib/components/ui/` holds the reusable parts: Panel (corner brackets), Button, IconButton, TextField, TextArea, Select, Toggle, Checkbox, Radio, Modal (dimmed, blurred backdrop with focus trap), Menu, Toaster, Banner, EmptyState, ErrorText, SaveIndicator, Icon, Wordmark/RingLogo, TitleBar, and the needs-attention pattern (AttentionBadge plus `ui/attention/` dialog with permission and question cards).
  - **Motion:** a reduced-motion store (`lib/stores/motion.svelte.ts`) follows macOS Reduce Motion and sets `data-motion="reduced"`, which turns off draw-in and pulse animations; durations are capped by tokens.
  - **Viewers and editors:** CodeMirror 6 with language packs for markdown, JSON, SQL and YAML (`lib/editor/languages.ts`); PDFs render with pdfjs-dist (`items/PdfViewer.svelte`); Markdown previews render with markdown-it and are sanitized with DOMPurify (`items/MarkdownPreview.svelte`).
  - **Editor theme:** CodeMirror 6 editors use a HUD theme (`lib/editor/hud-theme.ts`) that matches the tokens.
  - **Diff review:** a custom Svelte diff renderer (`lib/components/review/`, row building in `lib/review/diff-rows.ts`) draws the parsed hunks that the main process sends, in single-column or side-by-side layout, with windowed rows and line notes inline. No diff library and no syntax highlighting in diffs. The layout choice is a per-machine preference in `localStorage` (`arc.review.layout`); it is the only `localStorage` use.
  - **Guards:** unit tests enforce text contrast (4.5:1 / 3:1), the motion cap, no default Tailwind palette, that token utilities actually generate CSS, and that no Marvel names appear in the app.
- **Window chrome:** a frameless-style main window (`titleBarStyle: hiddenInset`, traffic lights at 16,14) with a full-width custom title bar (`ui/TitleBar`, a drag region) above every screen; minimum size 1100×720 and a `#03080F` background so no white flashes. Settings live in `src/main/app/window-options.ts`.
- **App menu:** a native menu (`src/main/app/app-menu.ts`) with App, File, Edit, View (reload and dev tools in development only, full screen, no zoom), Window and Help. Help › Design Preview opens the preview window.
- **Process layout:**
  - **Main process** - owns the session orchestrator, agent process supervisor, git service, persistence, and the local MCP bridge.
  - **Renderer** - chat UI, group/knowledge management, worker list, diff review, terminal panes. Two entries are built by electron-vite: `index.html` (the main app) and `preview.html` (the Design Preview).
  - **Design Preview window** - a single-instance secondary window (`src/main/app/preview-window.ts`) that shows every design-system component with sample content. It loads no preload, has no IPC access, and is not part of the close gate.
  - **Preload** - a typed IPC bridge (contextIsolation on, no Node in the renderer).
- **Agent runtime adapters:** one adapter interface (`start`, `send`, `interrupt`, `resume`, `events`) with Claude and Codex built and Cursor planned. A `ProviderRegistry` (`src/main/agents/provider-registry.ts`) exposes `adapter(p)`, `status(p)`, `models(p)` and `toolNamer(p)` per provider, and the session code starts agents through provider-neutral `CommonStartOptions` with a `claude` or `codex` block.
  - **Claude adapter** (`src/main/agents/claude-adapter.ts`) - spawns the local `claude` CLI headlessly (`-p --input-format stream-json --output-format stream-json`, `--model`, `--add-dir` per project, `--append-system-prompt` for group context, `--resume <session-id>`). It runs on the user's logged-in Claude subscription. Also passed, per spike S0 against CLI 2.1.302: `--verbose` (required with stream-json output), `--include-partial-messages` (live streaming), `--replay-user-messages`, `--setting-sources project` (keeps the user's permission rules and env out of agents), `--settings <generated hooks-only file>` (the user's own hooks, spec 007), `--plugin-dir <plugin view>` (below), `--mcp-config=<merged file> --strict-mcp-config` (the Arc bridge plus the user's own and plugins' MCP servers, spec 007), `--permission-prompt-tool mcp__arc__request_permission`, an explicit `--allowedTools` list for the brain, and `--permission-mode acceptEdits` for workers.
  - **Codex adapter** (spec 007, `src/main/agents/codex/`) - each Codex agent runs its own long-lived `codex app-server` (JSON-RPC 2.0, JSONL over stdio, `codex-rpc.ts`), pinned to and recorded against CLI 0.162.1 (`tests/fixtures/codex/0.162.1/`). It uses `initialize`, `thread/start`, `thread/resume`, `turn/start`, `turn/steer` and `turn/interrupt`, and parses `item/*`, `turn/*` and token-usage notifications into the same stream events as Claude (`codex-parser.ts`). It runs on the user's logged-in ChatGPT/Codex subscription with their real `CODEX_HOME` (a separate one drops the login), overriding per thread `model`, `modelProvider: 'openai'`, `approvalPolicy: 'untrusted'` with `approvalsReviewer: 'user'`, and the sandbox. Workers use `workspace-write` with writable roots limited to the worktree plus the git metadata it needs (`<common>/worktrees/<id>`, `objects`, `refs`, `logs`; no `/tmp`); the brain is `read-only`. Arc's bridge is added as the `arc` MCP server in the thread config (`bearer_token_env_var ARC_BRIDGE_TOKEN`, so the token stays out of argv, `tool_timeout_sec` 86400, `required`), and the user's own and plugins' MCP servers stay loaded. Tool names appear as `mcp__arc__*`, the same as Claude. Instructions go in `developerInstructions`. A no-model probe (`codex-probe.ts`) reads `model/list`, `skills/list`, `account/read` and `config/read`; if `config/read` fails Arc fails closed and treats every tool as needing approval.
  - **Agent load selection (spec 009, `src/main/personal/`)** - Settings has an **Agent loading** page (`AgentLoadSettings.svelte`, `LoadRow.svelte`, store `agent-load.svelte.ts`) listing the user's MCP servers, plugins, `~/.claude/skills`, hook events and Codex MCP servers, each with a Brain and a Workers switch and an estimate per request. Everything is on by default; `app_settings` key `agents.loadOff` stores only the item keys switched off for `brain` and for `workers` (workers and conflict resolvers; probes and the launch plan check are not affected). `LoadSelection` answers per role at each agent start, so a change applies to agents started afterwards. It filters the merged `--mcp-config` and the hooks-only `--settings` file in `PersonalConfigService` (Arc's own `arc` server is never switchable; with every hook event off there is no hooks file), the plugins and `~/.claude/skills` in `PluginViewService` (one view per role; a plugin that is off but enabled by a repository is written as a manifest-only stub so it still does not load), and, for Codex, writes `config.mcp_servers.<name>.enabled = false` on the thread. The command probe, the `/` list and the brain's command routing follow the Workers selection; `settings:set` refreshes the command catalogue and tells open brains when it changed. `BypassDetector` reports hook events per role (`BypassReport`), so the Providers warning lists Brain and Workers separately when they differ. `~/.claude/agents` is not loaded by Arc agents and `~/.claude/commands` stays always loaded. `LoadCatalogue` lists the items with `ceil(chars / 4)` estimates (`agent-load:get`; MCP sizes come from tool names an agent of this run reported, otherwise unknown; hooks are unknown), and the Codex servers come separately (`agent-load:codex`) so a slow Codex start never holds the page. The CLI-heavy Setup overhead suggestion links to the page.
  - **Cursor adapter** _(planned, later spec; not built)_ - drives the local Cursor CLI (`agent`, formerly `cursor-agent`) headlessly: `agent -p --output-format stream-json` (events: `system` init, `assistant`, `tool_call` started/completed, `result`), `--model`, `--workspace <path>`, `--resume <chatId>`. It runs on the user's Cursor plan after `agent login`. Arc's MCP bridge is given to it through a generated `.cursor/mcp.json` with `--approve-mcps`. _(assumptions: Cursor CLI takes one prompt per run with no stream-json input, so the adapter runs one process per turn and continues with `--resume <chatId>`, and `interrupt` means stopping that process; it has no permission-prompt tool, so approvals use its allow/deny permission config plus Arc's own command classification, and protected actions are denied rather than asked about until a hook or prompt mechanism is confirmed; extra repositories beyond `--workspace` may need to be reached through paths in the prompt.)_ The Cursor spec must also extend spec 008's token and plan-usage tracking to Cursor: token counts per agent from its stream events, its plan limits on the meters (or "Not reported" if the CLI doesn't expose them), the Usage page totals and the suggestions. _(assumption: which usage fields Cursor CLI reports needs a fixture check)_
  - All three CLIs are found on the user's PATH (`HARNESS_CLAUDE_BIN` / `HARNESS_CODEX_BIN` override them in tests). The app never handles credentials itself. If `OPENAI_API_KEY` is set, Codex may use it and Arc says so in Settings.
- **Provider status and updates (spec 007, `src/main/providers/`):** `ProviderStatusService` checks each CLI's version and sign-in (`claude --version`, `codex --version`, `codex login status`) when Arc opens, when the window regains focus and on Check again, and pushes `providers:changed`. It also re-reads each provider's model list (`src/main/models/model-registry.ts`; Codex's `model/list` is filtered per account) so new models appear without a restart, and fetches the latest published version from the npm registry (`registry.npmjs.org/@anthropic-ai/claude-code/latest`, `@openai/codex/latest`; cached 6 h, 5 s timeout; `provider-versions.ts`). A newer version shows on Settings › Providers with `claude update` / `codex update` and a copy button, plus a one-time dismissible notice per version (dismissals in `app_settings`). After an update new workers start on the new binary, the brain resumes its thread on it at its next reply, and running workers finish on the old one; when the running binary disappears Arc shows a "Restart Arc to finish updating" prompt (`app:relaunch`). Tests point it at a local file (`HARNESS_PROVIDER_LATEST_FILE`) and never reach the network.
- **Terminals:** every agent's output is rendered into a per-worker terminal buffer (`stores/worker-terminals.svelte.ts`) shown in a worker tab by `TerminalPanel.svelte`: a virtualized log with fixed 18px rows that soft-wraps long lines at the panel width (`terminal-wrap.ts`, column count measured from the monospace character width and recomputed on resize), so it never scrolls sideways. node-pty and xterm.js are not used; stepping in (below) talks to the same headless process. _(assumption: node-pty may still arrive with the planned plain shell and "Open in macOS Terminal" specs)_
- **Brain-worker communication (the MCP bridge):** the main process hosts a local MCP server (streamable HTTP on 127.0.0.1 on a random port) that every agent process, Claude or Codex, is configured to use. Each agent gets its own bearer token when it is registered; the token decides the agent's role (brain or worker) and so which tools it sees, and it is revoked when the agent ends. Calls that block for a long time (approvals, questions) send an MCP progress keepalive every 15 s (`src/main/bridge/keepalive.ts`) so neither CLI times out.
  - **Tools for the brain (built, `src/main/bridge/tools/`):** `spawn_worker(name, task, repos, provider, model, dependsOn, command)` (returns what the worker really runs on, with a note when the user's choice or availability overrode the brain), `message_worker`, `get_worker_status`, `merge_worker`, `sync_worker` (bring session-branch changes into a worker's worktree), `propose_plan` (each planned worker may name a `command`), `resolve_request`, `escalate_to_user`, `ask_user` (with optional `choices`). _Planned for later specs:_ Cursor as a `provider` value, `suggest_knowledge_update` (learning loop) and `get_usage` (usage awareness).
  - **Tools for workers (built):** `report_progress`, `report_done(summary, commits)`, `ask_brain(question)`, and `request_permission` (wired as the Claude CLI's permission-prompt tool). _Planned:_ `request_dependency(description)`.
  - **Approval and question escalation:** worker → brain → user.
    - **Workers:** workers ask questions with `ask_brain`.
    - **Claude permission prompts:** the Claude adapter passes `--permission-prompt-tool` pointing at a bridge tool (`request_permission`), so a headless worker's permission request becomes an MCP call instead of a hung prompt.
    - **Codex approvals (spec 007):** Codex sends server requests (`item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, `item/permissions/requestApproval`, `mcpServer/elicitation/request`). `codex-normalize.ts` turns each into a provider-neutral `NormalizedAction` (`src/main/policy/normalized-action.ts`), `classifyAction` applies the same rules as for Claude, and `AttentionCoordinator.requestAction` runs the usual brain-then-user flow (`src/main/sessions/codex-approvals.ts`). Arc answers only `accept`, `decline` or `cancel`, never a for-session or rule-amending accept, so later commands are still classified. Codex's `untrusted` policy asks for every command; the user's own Codex allow rules would skip both the sandbox and Arc, so Arc writes a per-worktree `.codex/rules/arc.rules` of prompt rules (excluded through the repo's shared `info/exclude`, `codex-rules.ts`), and a Codex brain gets an Arc-owned folder with the same file. Per-tool `approval_mode` overrides in the user's MCP config are replaced with prompt overrides. Stepping in sends `turn/steer` before declining, because an interrupt cancels pending approvals.
    - **Cursor approvals:** the Cursor adapter maps whatever approval signal Cursor CLI exposes onto the same flow. _(assumption: until one is confirmed, Cursor workers run with an allow list and Arc denies protected actions)_
    - **Pausing:** the orchestrator pauses the worker and records an `attention_request` (the worker, its kind — permission or question — the payload, and its status) in SQLite. It then hands the request to the brain, which can answer it with `resolve_request` or escalate it with `escalate_to_user`.
    - **Brain questions:** the brain can also call `ask_user` itself.
    - **Command questions (AskUserQuestion):** when a command in a worker asks the user a question, the CLI sends it through the permission tool. Arc shows it as a structured question card (choices, an Other box, Decline) and returns the answers as `updatedInput.answers`. These questions go straight to the user: Auto-approve skips them and the brain cannot resolve them. The brain itself is not allowed to call AskUserQuestion. Questions still pending at startup are cancelled.
    - **The user:** escalated requests are pushed to the renderer, shown through the amber needs-attention badge and attention dialog (`ui/AttentionBadge`, `ui/attention/`), and raised as a macOS `Notification` when the window isn't focused.
    - **Answers:** the user's approve, deny or answer is returned to the waiting tool call, so the worker resumes.
    - **Rules:** the orchestrator's policy decides what the brain may approve without the user, for example anything outside the worker's worktree or a destructive git command. Pending requests are restored when a session is resumed, and the workers stay paused until they are answered.
  - The orchestrator enforces the spawn mode: in plan-first mode `spawn_worker` is blocked until the user approves the plan, and in autonomous mode it respects the worker cap.
- **Splitting work:** the brain's prompt (`src/main/sessions/orchestrator.ts`, `BRAIN_PROMPT_VERSION` 4) tells it to give independent parts of a request to separate workers started together (usually one per repository or per independent sub-task), up to the worker limit, to keep sequential work in one worker, and to answer questions from reading when no code needs to run. Older sessions get a one-time note when the version rises.
- **Commands and skills (spec 005):** the user's Claude Code slash commands, skills and plugins run in Arc agents. Spec 005 kept their hooks and MCP servers out; spec 007 reversed that (below).
  - **Plugin view** (`src/main/plugins/plugin-view.ts`): PluginViewService builds a copy of the enabled user plugins under `userData/agent-plugins/<hash>/`; since spec 007 the copies keep commands, skills, agents, hooks and MCP definitions. It adds a `user` wrapper plugin for the personal commands and skills in `~/.claude` (listed as `/user:<name>`), and filtered copies of plugins a repository turns on in its `.claude/settings.json` `enabledPlugins`; a same-name copy shadows the raw plugin (spike S2). Every agent gets the view with `--plugin-dir`; since spec 009 there is one view per role (Brain, Workers), built without what the user switched off for that role (both current views are kept, `KEEP_VIEWS`). A repository's own committed hooks still run under `--setting-sources project`, and Arc logs a warning when it finds them.
  - **Command list** (`src/main/agents/command-probe.ts`): a no-model `control_request initialize` probe against the CLI, using the same flags, lists the commands. Each one is mapped to a source (`user`, `plugin:<name>` or `repo:<path>`) and cached. Codex skills (`skills/list`) and saved prompts (`~/.codex/prompts/*.md`, expanded by Arc) are added marked "Codex" (`src/main/agents/codex/codex-commands.ts`) and dropped when Codex isn't available. The renderer's `/` menu reads this list. A command always runs on its own provider, whatever the Workers setting says.
  - **Running commands:** a command always runs in a worker. `spawn_worker` and `propose_plan` take a `command`. The worker's first message is the command text, which the CLI expands. Workers record it in `workers.command` (migration 0021) and are labelled like "W2 · /awos:spec". The plan-first gate matches the approved command (`src/main/sessions/command-routing.ts`). The brain's prompt gets a "Commands available" block (`src/main/sessions/command-prompt.ts`) and a one-time note when plugins change.
  - **Helper agents:** helpers that a command starts run inside its worker. The stream parser emits `task-started`, `task-ended` and `tasks-changed`. The worker manager holds the worker's finish while helpers are running, with a 10-minute cap (`HELPER_CAP_MS`) and a 60 s grace period if no follow-up turn comes. Helpers show in the worker's terminal and as a "N helpers" chip, never as worker cards.
  - **Plugin management** (`src/main/plugins/plugin-service.ts`): PluginService wraps `claude plugin list/install/update/uninstall` (`--json` where available) plus a check for updates against the marketplace manifests. It runs one change at a time (`PLUGIN_BUSY`), reports the CLI's own error message (`PLUGIN_FAILED`) and streams progress as `plugins:progress`. After a change it rebuilds the view, refreshes the command list and notes the change for the brain. These are the same plugins Claude Code uses in the terminal. The renderer reaches it through `plugins:*` IPC from Settings › Plugins (the gear in the title bar).
- **Stepping in on a worker (spec 006):** the user takes over a worker in its tab and talks to the same long-lived headless `claude -p` stream-json process; no PTY or second CLI session is started.
  - **State:** `workers.user_control` (`active` | `paused` | null) is an overlay on the worker's status, which keeps its own value (migration 0022 also adds `control_started_at`, `control_user_messages`, `control_last_message`, `worker_worktrees.control_base_sha`, `attention_requests.route` and the `worker_held_messages` table). The renderer gets `userControl` and `controlReplying` on the worker view.
  - **IPC:** `workers:step-in`, `workers:hand-back`, `workers:send-input` (1–20,000 characters, sent verbatim, so slash commands work) and `workers:interrupt`.
  - **Step in:** sends an interrupt `control_request`, records the working tree's base sha, and suppresses Arc's own nudges and turn settling (`controlActive` guards). Queued, finished, merged, stopped and failed workers can't be stepped in.
  - **Approvals while controlled:** the worker's pending and new attention requests get `route='terminal'` and are pinned in the tab's "Needs your answer" group (Approve/Deny, no Always allow). Classification, allow rules and Auto-approve still run; protected actions always ask. The brain's `resolve_request` on them returns `not_resolvable`, and Needs-attention counts and the badge include only `route='queue'`.
  - **Brain lockout:** `message_worker`/`sync_worker` messages are held in `worker_held_messages` (`queued: true`), `merge_worker` is refused with `worker_user_control`, auto-merge skips the worker, and a `report_done` is recorded but doesn't stop it.
  - **Hand back:** one turn carrying the hand-back text, a note if the worker already reported done, and each held brain message in order; terminal requests go back to the queue; the brain gets a note with `diffStatSince` (working tree vs the base sha, untracked files included), the user's message count and last message.
  - **Leaving:** closing a controlled tab asks Hand back / Keep it paused / Cancel. Quit and startup run `pauseAllActiveControl()`, recovery skips controlled rows, and typing or Hand back on a paused worker relaunches it with `--resume`; the user's Stop ends control.
- **Personal MCP servers and hooks (spec 007, `src/main/personal/`):** Claude and Codex agents load the MCP servers and hooks the user set up for each CLI, their own and their plugins', but not their permission rules. For Claude, Arc reads `~/.claude.json` and `~/.claude/settings.json` read-only (`claude-user-config.ts`) and writes per-agent files: a hooks-only `--settings` file and a merged `--mcp-config`. For Codex the servers already load from the user's config. `mcp-tool-catalogue.ts` marks each personal MCP tool read-only (from its `readOnlyHint`) or changing; read-only tools run unasked and changing ones go through Arc's approvals showing the server, tool and arguments. Settings warns when the user's own config turns on a bypass mode (`bypass-detector.ts`), per role since spec 009. Since spec 009 the user can switch off each server, plugin, skill and hook event for the brain or the workers (see Agent load selection). Arc never writes to `~/.claude`, `~/.claude.json` or `~/.codex`.
- **Model and provider selection (spec 007):** Settings › Providers holds the defaults for new sessions in `app_settings`: a brain model from either provider (`ModelRef`, default Claude · Sonnet) and a Workers choice (`WorkersPref`: `auto`, a `provider`, or one `model`; default Auto). Each session overrides both from its header (`sessions.brain_provider`, `sessions.workers_pref_json`); a change applies from the brain's next reply and to new workers. `resolveWorkerTarget` (`src/main/models/provider-resolution.ts`) combines the brain's `spawn_worker` choice, the Workers setting, a command's own provider and availability. With Workers on Auto the brain picks the provider; its prompt (`BRAIN_PROMPT_VERSION` 5) suggests Codex for reviews and second opinions. The plan card shows and changes each worker's provider and model. Cards, the plan, worker details, terminal tabs and the event log show "Provider · model" (`ui/ProviderTag.svelte`).
- **Codex fallback (spec 007):** when Codex is not installed or not signed in, a worker meant for Codex runs on a comparable Claude model and the brain on Claude · Sonnet. The card shows "Claude (Codex unavailable)" and the event log says why and which command to run (`src/main/providers/fallback-text.ts`); `workers.requested_provider` and `workers.fallback_reason` record it. Switching the brain between providers starts or resumes that provider's own thread (`brain_threads`) and passes a short hand-off of the recent conversation (`src/main/sessions/brain-handoff.ts`).
- **Usage-aware selection** _(planned, later spec)_: live usage data from `get_usage` will steer the brain toward lighter models when limits are close.

## 2. Data & Persistence

- **App database:** SQLite through better-sqlite3 with Drizzle ORM, stored at `~/Library/Application Support/Arc/arc.db`. It holds groups, sections, project folder references, sessions, workers, plans, messages, events, attention requests, allow rules and merge history (workers also record the slash command they run, migration 0021, their user-control state, migration 0022, and their provider, migration 0023). Migration 0023 (`src/main/db/migrations/0023_codex_provider.sql`, hand-written because drizzle-kit would rebuild the tables) adds `app_settings` (key/value defaults and dismissed update notices), `brain_threads` (one provider thread or session id per session and provider), `sessions.brain_provider` and `workers_pref_json`, `workers.provider`, `requested_provider` and `fallback_reason`, and renames `claude_session_id` to `provider_session_id`, with backfills. Spec 008 adds the usage tables (migrations 0024-0028): `usage_turns` (tokens per agent turn), `agent_setup` (measured fixed setup and Arc's estimated additions per agent), `plan_limits` and `plan_notices`, `session_file_reads` and `usage_suggestions`; 0028 resets undismissed Setup overhead suggestions. Knowledge-update suggestions are _planned_ for the learning-loop spec. Change review adds `review_file_marks` (Reviewed ticks, keyed by a fingerprint of the file's base and tip blobs so a later change clears them), `review_notes` (line notes, draft or sent) and the latest push on `session_projects` (migrations 0015–0018); all cascade with the session. The renderer learns about review changes through the `session:review-changed` push event.
- **Session transcripts:** the canonical conversation history stays in each CLI's own session store (Claude and Codex session IDs and Cursor chat IDs are recorded per brain and worker so they can be resumed). The app also keeps a normalized event log per session in SQLite, so it can render history and resume quickly without re-parsing CLI files.
- **Knowledge (Notes, Docs, Playbooks, Links, custom sections):** plain files on disk (markdown, `.sql` schema dumps, etc.). By default each group's knowledge lives in `~/Library/Application Support/Arc/groups/<group-id>/knowledge/`, and a group can be linked to a user-chosen folder instead. Links are stored as a `links.md` (or one file per link) that agents can fetch.
- **Knowledge file access:** a chokidar 4 watcher (`src/main/knowledge/knowledge-watcher.ts`) picks up changes made outside Arc so open editors can offer Reload or Keep mine. The renderer never reads the disk directly: knowledge files are served through a custom privileged protocol (`src/main/protocol/knowledge-protocol.ts`) that only resolves paths inside a group's knowledge root.
- **Context delivery to agents:** at session start the app generates a group context manifest (the list of projects and knowledge files with short descriptions) and passes it as an appended system prompt. The knowledge directory is attached read-only via `--add-dir`, so agents read files when they need them rather than having everything inlined. _(assumption)_
- **Git state:** owned by each repo; the app records branch and worktree metadata only.
  - **Session branch:** `arc/<session-slug>`, created off `dev` (or the repo's default branch if `dev` is missing) and checked out in the user's **main checkout** of each project repo, so the user can look at the combined work directly in their own folder and editor.
  - **Uncommitted changes:** before switching branches, the app checks each repo for uncommitted changes. If any are found, it asks the user to stash them, commit them, carry them onto the session branch, or cancel; it never discards them. Resuming a session checks out that session's branch again (with the same check). _(assumption)_
  - **Worker worktrees:** `~/Library/Application Support/Arc/worktrees/<session-id>/<worker-id>/<repo>`, created detached (no branch of its own) at the current tip of the session branch. Git forbids checking out `arc/<session-slug>` in two places, and a nested `arc/<slug>/<worker>` ref can't coexist with `arc/<slug>`. The worker's HEAD sha is recorded after each commit.
  - **Merging:** `merge_worker` merges the worker's HEAD into the session branch in a temporary detached merge worktree, then moves `arc/<session-slug>`: by `merge --ff-only` in the user's main checkout when it is on the branch and clean (ref and files move together), by `update-ref` when the branch is checked out nowhere, and not at all when the checkout has unsaved changes (the merge waits under `refs/arc/pending/<slug>` and is applied later). On conflict, the orchestrator starts a short-lived resolver worker in the merge worktree (the brain never edits code); it escalates to the user only when it is not confident. Merges are queued one at a time per repo.
  - **Dependencies between workers:** `sync_worker` merges the updated session branch into the dependent worker's worktree and sends that worker a message describing the incoming change.
  - **Cleanup:** worker worktrees are removed after they're merged. Session branches are kept until the user deletes them; the app never merges into `dev`.
  - **Change review (`src/main/review/`):** `session_projects.base_sha` records where each session branch started (set at session start, backfilled once with `merge-base` for older sessions). The review is computed from git on demand — `diff --raw --numstat -z -M` from the base to the effective tip (the pending ref when a merge is waiting), per-file patches fetched lazily — and cached in memory by repo, base and tip. Worker attribution maps the commits in that range to workers through `worker_commits` and `merges`; anything unmapped shows as "You". The user's uncommitted edits are listed separately and only when their checkout is on the session branch.
  - **Undo:** reverting one file's session changes builds a commit in the temporary `_merge` worktree and publishes it exactly like a merge, inside the per-repo merge queue; the brain is told through a deferred note.
  - **Push:** the only way Arc pushes is the review's Push branch button. A dedicated runner (`src/main/git/push.ts`) runs exactly `git push -u <remote> arc/<slug>` with the user's SSH agent (`SSH_AUTH_SOCK`, `ssh -o BatchMode=yes`), no terminal prompts and a 120 s timeout, after the user clicks Push in a dialog showing that command. It is reachable only from a renderer IPC call (`confirm: true`), never from the MCP bridge; a unit test scans the source to enforce both.
- **Git tooling:** the system `git` binary called through a thin typed wrapper (`src/main/git/git.ts`, child_process) with an allowlist of subcommands. Beyond the read and branch operations, it permits exactly two narrow forms: `checkout <40-hex sha> -- <path>` (Undo) and, only in the push runner built with `allowPush`, `push -u <remote> arc/<slug>`. Every diff passes `--no-ext-diff --no-textconv`. _Alternative: simple-git._

## 4. External Services & APIs

- **AI providers:** reached only through the locally installed CLIs:
  - Claude Code (`claude`, currently 2.1.x on this machine) using the Claude subscription.
  - Codex CLI (`codex`, currently 0.162.x) using the ChatGPT/Codex subscription.
  - Cursor CLI (`agent`) using the Cursor subscription.
  - No direct API keys, and no Anthropic/OpenAI SDK calls from the app.
- **Claude Code plugins:** managed through the `claude plugin` subcommands, which use Claude Code's own marketplaces and plugin cache under `~/.claude/plugins/`. Arc only reads that cache to build its filtered view and never edits it directly.
- **Authentication:** handled entirely by the CLIs' own login flows. The app only detects logged-out or missing CLIs (Settings › Providers: "signed in", "not signed in", "not installed") and tells the user which command to run (`codex login`, `npm install -g @openai/codex`).
- **Usage & rate limits (spec 008, `src/main/usage/`):** each adapter reports token usage per turn in four buckets (input uncached, cache write, cache read, output). `UsageRecorder` (`usage-recorder.ts`) saves one `usage_turns` row per agent turn at turn end and keeps the in-flight count of a running turn (Claude's parser emits `usage-progress` with the running total; Codex reports mid-turn), so the cards, header chip and panel rise live while saved rows stay the only source for the Usage page, suggestions and plan notices. The first request of each new agent gives its measured fixed setup (`agent_setup`), compared with `setup-estimator.ts`'s estimate of what Arc adds. Weighted totals use per-provider weights in `src/shared/usage-weights.ts`. Plan limits: `PlanUsageService` keeps the newest observation of each limit window per provider (`plan_limits`) from Claude's `rate_limit_event` and Codex's rate-limit reads (`codex-rate-limit-reader.ts`, every 5 minutes and on focus); an optional Claude plan check on launch (`claude-plan-probe.ts`, one tiny request on the lightest model, recorded as a `plan_check` row) fills the meter before any agent runs. `plan-notices.ts` raises 80% and 95% notices (`plan_notices`). `SuggestionService` writes deduplicated suggestions (`usage_suggestions`; repeated file reads come from `session_file_reads`), including Setup overhead, and `usage-report.ts` builds the Usage page report. IPC: `usage:get-session`, `usage:get-report`, `usage:dismiss-suggestion`, `plan:get`, `plan:refresh`, `plan:dismiss-notice`, with throttled `usage:session-changed`, `usage:changed` and `plan:changed` pushes. The renderer shows plan meters in the header, a per-session token panel and the Usage page (`components/usage/`). A rate limit still pauses the agent with one retry. `get_usage` for the brain is _planned_ with usage-aware selection.
- **npm registry:** the only network call Arc makes itself is a read of the latest published Claude Code and Codex versions (spec 007), cached for 6 hours. Everything else goes through the CLIs.
- **Web content for Links:** fetched by the agents' own web-fetch tools.

## 5. Security

- **Typed, validated IPC:** every channel is declared once in a shared contract (`src/shared/ipc/contract.ts`) and every message is checked with zod; the preload exposes only that contract (contextIsolation on, no Node in the renderer).
- **Content Security Policy:** a strict CSP is applied as a meta tag in production builds and as a response header in development (`src/main/app/csp.ts`).
- **Window lockdown:** `src/main/app/lockdown.ts` denies new windows and blocks navigation away from the app's own pages.

## 6. Observability & Monitoring

- **App logging:** electron-log 5 (`src/main/logging.ts`) writing one `main.log` under `~/Library/Logs/Arc/`, with scopes `ipc`, `knowledge`, `cli`, `sessions` and `db`. No rotation is configured beyond electron-log's defaults. Agent output is not in this log; it lives in per-agent transcripts (below).
- **Agent visibility:** each agent's raw output is kept in its terminal buffer, and the normalized events are kept in SQLite. The UI shows live worker status, current activity, model, and token usage.
- **Session audit trail:** plans, approvals, spawns, merges, conflict resolutions, and hand-offs between workers are recorded as session events, so any session's history can be replayed and inspected.
- **Crash handling:** the main process catches child-process exits and marks workers as failed, keeping their worktree for inspection. There is no Electron crashReporter and no remote telemetry; a local-only crashReporter is a possible follow-up.
